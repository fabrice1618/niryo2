# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Nature du dossier

Ce n'est pas un dépôt de code mais le dossier d'un **cours** : « Infrastructure client / serveur dans un contexte industriel » (année 2026-2027). Tout le contenu est rédigé en **français**, en Markdown avec des schémas Mermaid. Il n'y a ni build, ni tests, ni lint.

Le cours est **modulaire** : un même socle de supports est décliné en **trois progressions pédagogiques**, une par classe. Chaque classe pioche dans les supports selon son volume horaire, son niveau et son calendrier.

## Organisation

- `progression_pedagogique/` : une progression par classe, nommée d'après le code de la promotion. Les trois classes : `BACHINGE24` (BACH INGE 2024-0, 3e année, alternants, groupes G1 et G2), `B3RNSPP26` et `BACHTECH24`. Les trois fichiers existent (`BACHINGE24.md`, `B3RNSPP26.md`, `BACHTECH24.md`) et suivent le même modèle ; les plannings sources sont les `seances_*.xlsx` du même dossier. Une progression contient : intention générale, compétences visées (C1 à C6), architecture cible, tableau des séances (5 séances pour BACHINGE24, 12 pour B3RNSPP26, 13 pour BACHTECH24), détail de chaque séance (fiche lieu / groupes / durée / matériel, objectifs, déroulé minuté, livrables, supports de cours, ressources reprises), configuration du serveur, points à arbitrer. Les séances s'écrivent en toutes lettres (« séance 3 », « séances 3 et 4 »), jamais en abrégé « S3 ».
- **La séance 1 est commune aux trois classes** (prise en main du robot, export Python, définition du process) : même durée (3h30), même déroulé, mêmes livrables. Son contenu détaillé est dans `cours/01_prise_en_main_robot.md` ; dans chaque progression, la séance 1 garde la même fiche et ne diffère que par le créneau, les groupes et le délai avant le retour au robot. Modifier la séance 1 suppose de modifier `cours/01_prise_en_main_robot.md` et les trois progressions ensemble.
- `progression_pedagogique/presentation_BACHINGE24.md` : présentation Marp du module pour la classe BACHINGE24, exportée en `presentation_BACHINGE24.pdf` (skill `marp-export-pdf`). Elle suit d'abord le narratif du `README.md` (contexte, besoins, objectifs, fonctions, synoptique, données, démarche), puis la progression `BACHINGE24.md` (séances, rythme, livrables, fournitures, connaissances, scénario de tâches) : la mettre à jour, puis régénérer le PDF, quand le README ou la progression change. Marp ne rend pas Mermaid : ses schémas sont des sources `img/src/*.mmd`, rendues en `img/*.svg` avec `mmdc`. Il n'y a pas de PDF des progressions elles-mêmes.
- `progression_pedagogique/presentation_B3RNSPP26.md` : présentation Marp du module pour la classe B3RNSPP26, sur le même modèle (même partie README, adaptée : fonction F9 Grafana, NUC du fab lab et schéma `img/reseau_IRUP.svg`, équipes `r1e1` à `r1e4` et leurs ports ; puis les 12 séances de la progression `B3RNSPP26.md`), exportée en `presentation_B3RNSPP26.pdf`. La mettre à jour avec la progression, comme celle de BACHINGE24.
- `progression_pedagogique/materiel_ISTP.md` et `materiel_IRUP.md` : besoins en matériel, réseau et vérifications en amont, par établissement. ISTP (BACHINGE24) : serveur Raspberry Pi, séances en salle D3.10 sur un réseau séparé puis au fab lab. IRUP (BACHTECH24 et B3RNSPP26, effectifs inférieurs à 12) : serveur NUC du fab lab démarré sur disque externe, inaccessible depuis la salle de cours, donc toutes les séances avec serveur ont lieu au fab lab. Les identifiants d'équipe sont propres à chaque classe (`g1e1` à `g2e4`, `t1e1` et `t1e2`, `r1e1` à `r1e4`), avec un thème de noms par classe (métaux, étoiles, fleuves).
- `analyse/` : trois documents que les équipes renseignent et présentent. `cahier_recette.md` (cahier de recette présenté le jour de l'évaluation : deux tests entièrement rédigés, T01 commande de l'anneau de LED depuis le site et T02 message mal formé, à adapter par les équipes, un modèle pour les autres, fiche de passage signée ; ses exigences E1 et E2 sont préremplies dans le dossier d'analyse). `questions.md` (questions individuelles posées à chaque étudiant le jour de l'évaluation : 30 questions de compréhension, sur le rôle des éléments et des échanges, **sans aucune technique** ni protocole, code ou commande ; avec les endroits où chercher, sans réponses). `dossier_analyse.md`, gabarit du dossier d'analyse que chaque équipe renseigne (cases `À COMPLÉTER`, renseigné au fur et à mesure et rendu une seule fois, à la fin du projet : pas de versions intermédiaires) : identité de l'équipe, process, poses, architecture, connexions (serveur, broker, robot, ports), liste exhaustive des paramètres en tête de chaque programme fourni, messages MQTT et dictionnaire des champs, tables SQLite, endpoints de l'API et routes du site (ceux des programmes fournis sont préremplis), exigences. Ses valeurs préremplies sont celles des programmes fournis : **les modifier ensemble** (paramètre, message, table ou endpoint changé dans le code, puis dans ce gabarit). Aucun mot de passe dans ce document.
- `INSTALLATION_POSTE.md` : fiche d'installation du poste de développement des étudiants (Windows en priorité) : Python, VS Code, SSH, WinSCP, DB Browser for SQLite, MQTT Explorer, `curl.exe`, vérification du poste. Elle tient lieu du « Howto du poste de développement » de la progression BACHINGE24 ; le script `verifier_poste.py` annoncé dans cette progression n'existe pas.
- `lancer.py`, `requirements.txt` : lancement en local, depuis la racine, pour des étudiants qui travaillent le plus souvent sur Windows (`python lancer.py collecteur|site|api|mqtt`, un programme par terminal). `lancer.py` utilise l'environnement Python `venv/` sans qu'on l'active (pas de `Activate.ps1`), le crée avec `requirements.txt` au premier lancement, crée `cellule.db` à la racine s'il le faut, et fixe le dossier courant à la racine (les programmes cherchent `cellule.db` dans le dossier courant). `venv/` et `cellule.db` ne sont pas versionnés. Les étudiants modifient les paramètres en tête des programmes en place (pas de copie). `api_robot/` et `essai_robot/` s'exécutent sur le robot, pas dans cet environnement. Mode d'emploi : `site_web/README.md`, section « Lancement en local ». Sur le serveur du module, on lance toujours `python3 programme.py` depuis `~/supervision`.
- `scripts/` : outils de préparation du matériel. `creer_comptes_equipes.sh` crée les comptes Linux des équipes avec des mots de passe aléatoires (postes D3.10, Raspberry Pi, NUC).
- `install/` : installation des serveurs du module, pas à pas. `install_raspberry.md` (Raspberry Pi d'ISTP, SQLite) et `install_nuc.md` (NUC de l'IRUP, SQLite et Grafana, qui lit la base `~/supervision/cellule.db` de chaque équipe en lecture seule avec l'adaptateur `frser-sqlite-datasource`, avec une source de données, un compte et un dossier Grafana par équipe) : Ubuntu Server 24.04, réseau, comptes, Mosquitto ouvert, sans compte ni ACL (réseau local du module ; chaque équipe publie sous `cellule/<equipe>/` par convention), environnement Python commun `/opt/cellule/venv`, vérifications, sauvegarde.
- `install_robot/` : installation hors ligne, sur chaque robot Ned2, des bibliothèques Python du projet (Flask, paho-mqtt) dans `~/cellule/libs`, sans toucher au Python du système Niryo. `paquets/` contient les fichiers `.whl` (ARM 64 bits, Python 3.8 à 3.12, versions fixées dans `requirements.txt` pour rester compatibles avec Python 3.8) ; `install.sh` installe, `lancer.sh` lance un programme avec ces bibliothèques et l'environnement ROS, `test.py` vérifie l'installation, `telecharger_paquets.sh` régénère `paquets/`.
- `simulateurs/` : les deux simulateurs fournis aux équipes, paramètres en tête de chaque fichier. `simulateur_mqtt.py` envoie au choix, dans un menu, les messages du robot pour tester le collecteur (cycles, état, défaut, tâche, messages mal formés, production, rafale, message libre) ; `simulateur_api.py` a les endpoints de l'API du robot sans robot (chaque appel est affiché, puis la tâche est simulée par une attente, avec les mêmes réponses et les mêmes messages MQTT).
- `collecteur/` : collecteur MQTT fourni, version simplifiée du squelette de `cours/collecteur_MQTT.md`, paramètres en tête de chaque fichier. `creer_bdd.py` crée `cellule.db` (tables `messages`, `robots`, `cycles`) et enregistre le robot de l'équipe ; `collecteur.py` s'abonne à `cellule/<equipe>/#`, dépose chaque message dans une file d'attente, et un fil écrivain les écrit un par un dans `messages` et tire les fins de cycle dans `cycles` (`enregistrer_cycle`) ; session persistante. Les deux se lancent depuis `~/supervision/` sur le serveur. `README.md` : mode d'emploi, vérifications, messages d'erreur, adaptation (ajouter une table).
- `site_web/` : base du tableau de bord (site Flask), volontairement minimale, à copier dans `~/supervision/` avec le collecteur. `supervision.py` (paramètres en tête : `URL_API`, simulateur d'API ou robot, `BASE`, `PORT_SITE`) : `GET /` la page, `GET /etat` le morceau de page « état du robot (`GET /robot/etat`) et 20 derniers messages de la table `messages` », rechargé toutes les 2 s par quelques lignes de JavaScript, une route `POST /commande/<tâche>` par bouton qui relaie la commande à l'API avec `requests` (`timeout=1` : l'API ne répond qu'à la fin de la tâche, le site n'attend pas) puis Post / Redirect / Get avec `flash`. Templates `accueil.html` et `etat.html`, `static/style.css`. Modèles commentés pour ajouter une commande (route et bouton).
- `api_robot/` : API fournie, exécutée sur le robot (Python ROS Wrapper, port 3000), qui reprend les scripts d'essai 7 à 9 : `GET /robot/etat`, `POST /robot/home`, `/robot/autocalibrate`, `/robot/ledring/<couleur>`. Code volontairement simple, pour des étudiants qui ne sont pas développeurs : un endpoint par tâche (`home()`…), qui vérifie que le robot est libre, appelle `commencer()`, fait les appels au robot dans un `try`, puis renvoie `terminer()` (ou `echec()` en cas d'erreur) ; le simulateur a la même forme, avec une attente et sans `try` ; une tâche à la fois (`409` « robot occupé » sinon), réponse à la fin de la tâche (`500` en cas d'erreur du robot), `GET /robot/etat` immédiat avec `tache_en_cours` pour le tableau de bord, `debut_tache` puis `fin_tache` (statut `terminee` ou `erreur`) publiés sur `cellule/<equipe>/tache`. Pour ajouter une tâche, on copie le modèle en fin de fichier, dans l'API et dans son simulateur.
- `essai_robot/` : scripts d'essai à exécuter sur le robot (Python ROS Wrapper), repris de l'an dernier et adaptés aux conventions du projet, avec leurs énoncés dans la partie 7 de `cours/01_prise_en_main_robot.md` (les scripts en sont les corrigés). Paramètres communs dans `config.py` ; scripts 1 à 3 (calibration, convoyeur, cycle), 4 et 5 (MQTT), 6 et 7 (API, port 3000), 8 (`lire_etat(n)`, état du robot) et 9 (`GET /robot/etat`). Topics d'essai `cellule/<equipe>/essai` et `cellule/<equipe>/led`, distincts des topics du projet. Avec `scripts/`, `install_robot/`, `simulateurs/`, `collecteur/`, `site_web/` et `api_robot/`, c'est le seul code du dossier.
- `cours/` : les supports de cours, **communs aux trois classes et donc génériques** : aucune mention de promotion, d'année d'étude, de date de séance ni de numéro de séance (« séance 1 »…), car le découpage en séances diffère d'une classe à l'autre. Pour situer un moment du projet, parler de l'étape (« lors de la prise en main du robot », « tant que le robot n'est pas intégré », « lors de l'intégration ») et renvoyer aux autres supports par leur titre. La correspondance supports / séances se trouve uniquement dans les progressions. Chaque support commence par un titre, la ligne d'en-tête `Infrastructure client / serveur dans un contexte industriel`, puis un paragraphe qui situe le support dans le projet fil rouge. Les identifiants d'équipe (`g1e1`) et les dates des données d'exemple sont de simples exemples et peuvent rester. **Seule exception** : `cours/01_prise_en_main_robot.md`, support de la séance 1, qui peut porter ce numéro puisque la séance 1 est la même pour toutes les classes (il reste sans promotion ni date). Sa partie 7 (scripts d'essai sur le robot) sert aussi lors de l'intégration et reste rédigée par étape.
- `documentation_Niryo_Ned2/` : documentation du constructeur (PDF Niryo : robot Ned2, Niryo Studio, accessoires, ressources pédagogiques NiryoAcademy). Sert de référence pour les supports qui touchent au robot ; `cours/01_prise_en_main_robot.md` y renvoie. Documentation en ligne du logiciel du robot (pile ROS, Python ROS Wrapper) : <https://niryorobotics.github.io/ned_ros/>, dont l'index principal et les pages utiles au projet sont repris dans la partie 9 de `cours/01_prise_en_main_robot.md` ; les autres documents renvoient vers ses pages précises (référence du wrapper, état du matériel, convoyeur).
- `*.drawio` / `*.drawio.png` : schémas d'architecture (draw.io) à la racine.
- Les supports de l'année précédente (pile MySQL, Docker, Node-RED, Grafana) sont dans le dossier du cours 2025-2026, hors de ce dépôt ; les progressions y font référence dans les rubriques « Ressources reprises de l'an dernier ».

## Le projet fil rouge (fil conducteur de tous les supports)

Chaque équipe réalise une **cellule robotisée supervisée** :

robot Niryo Ned2 + convoyeur (capteur DI5) → publication MQTT → broker Mosquitto → collecteur Python → base SQLite → site web Flask (tableau de bord) → API Flask de commande CQRS → robot.

Les supports de `cours/` sont tous rattachés à ce fil rouge et partagent des conventions qui doivent rester **cohérentes entre fichiers** (en modifier une suppose de vérifier les autres supports et les progressions) :

- Topics MQTT : `cellule/<equipe>/cycle`, `cellule/<equipe>/etat` (retenu), `cellule/<equipe>/defaut`, `cellule/<equipe>/tache` (début et fin des tâches de l'API du robot : `debut_tache`, `fin_tache`), avec `<equipe>` de la forme `g1e1`.
- Message JSON : `{"evenement": "fin_cycle", "piece": 12, "duree": 18.2, "zone": "A", "horodatage": "..."}`.
- Tables SQLite : `messages(id, recu_le, sujet, charge, qos, retain)`, `robots(id, nom, equipe, adresse_ip)`, `cycles(id, robot_id, debut, duree, zone, statut)` ; fichier `cellule.db`.
- API CQRS : `GET /requetes/etat`, `POST /commandes/demarrer`, `/commandes/arreter`, `/commandes/calibrer` (réponse `202 Accepted` + id de commande), classe `RobotSimule` pour le mode simulé. L'API fournie (`api_robot/`) et son simulateur (`simulateurs/simulateur_api.py`) sont plus simples : routes `/robot/…`, réponse à la fin de la tâche.
- Ports : API simulée 5001 à 5008, site web 8001 à 8008 (une valeur par équipe), API sur le robot port 3000 (le port 5000 du robot est pris par le serveur Flask du logiciel système de Niryo, par lequel passe Niryo Studio), MQTT 1883.
- Réseau du fab lab : `192.168.10.0/24`, serveur en `.10` (NUC de l'IRUP ; le Raspberry Pi d'ISTP prend `.11` quand il vient au fab lab), robots en `.21` à `.24`.
- Programmation du robot (option retenue) : tout le code du robot utilise le **Python ROS Wrapper** et s'exécute **sur le robot** : l'export Python de Niryo Studio (`n = NiryoRosWrapper()`), le programme process et l'API de commande (adaptateur `RobotNiryo()` de `API_CQRS_REST_Flask.md`). Les programmes sont copiés par `scp` et lancés par `~/cellule/lancer.sh` (voir `install_robot/`), avec un nom de nœud ROS propre à l'équipe (`rospy.init_node('cellule_g1e1')`, pas `niryo_blockly_interpreted_code`). `pyniryo` (`NiryoRobot(ip)`, TCP port 40001, depuis un autre poste) n'est pas utilisé dans le socle : seulement pour l'extension vision de BACHTECH24. Poses nommées `pose_attente`, `pose_prise`, `pose_depose_A` (`POSE_ATTENTE`, `POSE_PRISE`, `POSE_DEPOSE` dans l'API). Capteur infrarouge sur DI5 : `HIGH` sans pièce, `LOW` pièce détectée (à vérifier sur chaque convoyeur).
- Pile volontairement allégée : SQLite (pas MySQL), pas de Docker, pas de Grafana ni de Node-RED ; le tableau de bord est le site Flask. Exceptions : la progression `BACHTECH24` ajoute la vision OpenCV (caméra du robot) et un dashboard Grafana, la progression `B3RNSPP26` ajoute le même dashboard Grafana ; sur le NUC, Grafana lit directement la base SQLite de chaque équipe (adaptateur `frser-sqlite-datasource`, lecture seule), sans MySQL ni double écriture ; leurs supports `vision_OpenCV.md` et `dashboard_Grafana.md` sont à écrire dans `cours/`, en restant génériques.

## Conventions de rédaction

- Français, phrases simples, registre de cours. Pas de tiret cadratin (« — ») : utiliser « : », « , » ou des parenthèses.
- Schémas en blocs ```` ```mermaid ```` (flowchart, sequenceDiagram, gantt), libellés entre guillemets avec `<br/>` pour les retours à la ligne.
- Tableaux Markdown pour les déroulés de séance (`Durée | Activité`) et les correspondances supports / séances.
- **Programmes fournis aux étudiants** (`simulateurs/`, `collecteur/`, `site_web/`, `api_robot/`, `essai_robot/`, ainsi que le code des supports) : les étudiants ne sont pas développeurs, ils doivent pouvoir lire et adapter ces programmes. Les garder **simples et courts** : script à plat, paramètres à adapter en tête de fichier, quelques fonctions aux noms explicites, commentaires en français, messages d'erreur clairs. Pas d'abstraction (classes, listes de fonctions, gestion de signaux, options en ligne de commande) ni d'optimisation (écriture par lots) sans besoin réel en séance ; une précaution de robustesse ne se justifie que si elle évite une perte de données ou un blocage fréquent. Ce qui sort du programme (création de la base, par exemple) va dans un script à part. Expliquer les choix et les limites dans le `README.md`, pas dans le code.
- Quand un support est ajouté ou renommé dans `cours/`, mettre à jour le tableau « Supports de cours » (fin de la section 4) et les rubriques « Supports de cours » des séances concernées dans chaque progression.
